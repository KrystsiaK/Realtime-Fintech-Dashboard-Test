# Realtime Fintech Dashboard

Angular app with a live market table. Market data is generated by a Rust library compiled to WebAssembly, which runs inside a Web Worker.

Live demo: https://krystsiak.github.io/Realtime-Fintech-Dashboard-Test/

## Stack

- Angular 22 (standalone components, zoneless, signals, Signal Forms)
- Tailwind CSS 4
- Rust -> `wasm32-unknown-unknown`, exported through a plain C ABI (no wasm-bindgen)
- Vitest for TypeScript tests, `cargo test` for the generator
- GitHub Actions -> GitHub Pages

## Getting started

You need Node 24.15+ (see `.nvmrc`) and Rust with the wasm target:

```bash
rustup target add wasm32-unknown-unknown
npm ci
npm start
```

`npm start` builds the wasm module first and then runs `ng serve` on http://localhost:4200.

Other scripts:

```bash
npm run build      # wasm release build + production Angular build
npm test           # Angular unit tests (Vitest)
npm run test:wasm  # Rust generator tests
npm run test:all   # both
```

## How it works

```
Angular (main thread)                    Web Worker
---------------------                    ----------
MarketDataStore  -- start/pause/resume -->  producer-engine
  signals, runId                              setInterval(batchInterval)
  rows = computed(...)  <-- snapshot ------   producer_generate() in wasm
                                              applyBatch() -> running totals
```

**Generator (`wasm/producer`).** Keeps state per instrument (mid price, book sizes) between calls. The price is a small random walk (up to 0.1% per update) with a $1 floor. The spread is at least 1 cent, so bid < ask, and the trade price is either the bid or the ask. Randomness comes from a seeded xorshift64* PRNG, which makes the Rust tests deterministic.

**Wasm -> worker.** Each update is 7 i32 values written into a reused `Vec<i32>`. The worker reads them with an `Int32Array` view over wasm memory. The view is created after every call because memory growth detaches old buffers.

**Metrics.** Aggregated in the worker (`metrics.ts`). Only running totals are kept: last trade, latest bid/ask and book sizes, volume, and sum(price * qty) in integer cents. Every trade is counted once, and there is no event history. The main thread gets one small snapshot per batch (at most 50 objects), so UI work doesn't grow with the update rate. Cents are converted to dollars only for display.

**Runs.** Every Apply increments `runId`. The worker tags all messages with it, and the store drops anything from an older run. Pause and resume just stop and restart the interval, so nothing is generated for the paused time.

**One producer.** `MarketDataStore` is a root singleton, so switching pages doesn't create another worker or reset the run. A new run frees the previous wasm generator, and the worker is terminated when the app is destroyed.

**Errors.** Commands are processed in order, including while wasm is still loading, and a failed command doesn't block the next one. If wasm fails to load or traps, the run stops and the error is shown in the UI. The failed instance is dropped as a whole, and the next Apply creates a new instance from the cached compiled module. A failed download is retried on the next Apply.

The worker logic lives in `producer-engine.ts` and doesn't depend on worker globals, so it can be tested with fake timers and a fake wasm module. `producer.worker.ts` only loads wasm and forwards messages.

## Tests

- `metrics.spec.ts`: worked example from the task, zero denominators, separate instruments, totals across batches
- `settings.spec.ts`: validation (range, integer, required), editing doesn't affect the producer until Apply
- `market-data.store.spec.ts`: pause/resume, Apply resets values and restarts a paused run, results from an old run are ignored, only one worker is created
- `producer-engine.spec.ts`: worker behaviour with fake timers (interval, pause, resume without catch-up, commands sent while wasm is loading, error recovery, replacing a failed wasm instance)
- `wasm/producer/src/lib.rs`: batch size, value invariants, price continuity, determinism

## Deployment

`.github/workflows/deploy.yml` runs the tests, builds the app, and deploys every push to `main` to GitHub Pages (Settings -> Pages -> Source: GitHub Actions). The app uses hash routing, so links like `/#/settings` work on static hosting without extra setup.
